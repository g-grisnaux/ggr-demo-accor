# demo-accor — Accor BFF observability demo

## Instrumentation mode: `ddot`

This project uses the Datadog SDK with the DDOT Collector. Custom spans in generated business logic may use either the DD tracer API or the OTel API — both flow through the DDOT pipeline.

## Stack
- Node.js Express + Apollo Server 5: graphql-bff (8080), payment-api (8083)
- Java Spring Boot: hotel-search-api (8081)
- Python Flask + gunicorn: booking-api (8082)
- Frontend: React (Vite) (frontend/), service name `all-web`
- Infrastructure: Kubernetes on GKE (europe-west9-a), Terraform under service
  account impersonation
- Dependencies: db:postgresql (schema and seed in deps/postgresql/)

## Launch

```bash
./scripts/deploy-gke.sh
```

See README.md for the prerequisites — real Datadog credentials in .env and
roles/artifactregistry.admin on the impersonated service account are both
required, and neither is in place by default.

## Architecture

Services carry the full booking domain. The BFF is layered the way the Accor
BFF is: resolvers -> repositories (business rules + dataloaders) -> API clients
-> DTO mappers, with a fixed business error taxonomy in `src/errors.js` and the
GraphQL-level metrics in `src/telemetry.js`.

| Service | Port | Backend | Role |
|---------|------|---------|------|
| graphql-bff | 8080 | node:express | Public GraphQL entry point |
| hotel-search-api | 8081 | java:spring | Search + availability, PostgreSQL |
| booking-api | 8082 | python:flask | Bookings, calls payment-api |
| payment-api | 8083 | node:express | Payment authorization |

Manifests are generated by `scripts/render-manifests.py` — edit the SERVICES
list there rather than the YAML.

## Datadog — Baseline Instrumentation

These are always active (no configuration needed):
- **APM**: Auto-instrumented on all services. Distributed traces propagate across service boundaries.
- **Logs**: JSON on stdout, collected by the Datadog Agent. Correlated with traces via dd.trace_id/dd.span_id.
- **Infrastructure**: Container metrics and host metrics via the Agent.
- **RUM**: Browser SDK initialized. Sessions captured and connected to backend traces.

## Project Rules

### Unified Service Tagging

All telemetry must include `env`, `service`, and `version` tags:

- **env**: Set via `DD_ENV` in `.env`. Currently `demo-accor-260907`. Must stay lowercase — Kubernetes namespaces and Docker repository names both reject uppercase.
- **service**: Unique per service, consistent across traces/logs/metrics. Set via `DD_SERVICE`.
- **version**: Set via `DD_VERSION`. Use `1.0.0` or git SHA.

Tags are configured via environment variables in docker-compose.yml — do not hardcode in application code.

### Secrets Management

- **Never** commit API keys or secrets to version control.
- All credentials live in `.env` (gitignored). `.env.example` documents required variables.
- Required: `DD_API_KEY`, `DD_SITE`, `DD_RUM_APPLICATION_ID`, `DD_RUM_CLIENT_TOKEN`

### Logging

- All services emit **JSON logs to stdout** (one object per line).
- Required fields: `message`, `level`, `timestamp`.
- Trace correlation fields (`dd.trace_id`, `dd.span_id`) are injected automatically by the tracer.
- Do not use plain-text log formats — JSON enables zero-config parsing by the Datadog Agent.

### Telemetry Validation

After any code change, verify telemetry is flowing:
1. Check service appears in APM Service Catalog
2. Check logs are correlated with traces (dd.trace_id present)
3. Check distributed traces span multiple services
4. Use the `verify-telemetry` skill for automated checks (requires Datadog MCP)
